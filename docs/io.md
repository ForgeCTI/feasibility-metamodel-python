# I/O

The `io` module manages how CTI Feasibility Metamodel scenarios enter and leave the package.

It is responsible for parsing scenario files, serializing model objects, and importing CTI sources such as STIX bundles.

## Purpose

The **CTI Feasibility Metamodel** can be created directly in Python, but many scenarios are easier to maintain as files.

The `io` module supports workflows such as:

```text
scenario.yaml      → Model
scenario.json      → Model
STIX bundle.json   → Model
draw.io diagram    → Model
Model              → scenario.json
Model              → scenario.yaml
```

This makes the package usable for:

* repeatable case studies;
* version-controlled scenario definitions;
* automated validation pipelines;
* conversion from CTI feeds;
* graph export after parsing;
* documentation and reproducibility.

## I/O versus adapters

The package distinguishes between `io` and `adapters`.

| Component  | Responsibility                                                       | Example                         |
| ---------- | -------------------------------------------------------------------- | ------------------------------- |
| `io`       | Reads and writes scenario files or CTI input formats.                | JSON, YAML, CSV, draw.io, STIX. |
| `adapters` | Converts a validated model to or from external libraries or systems. | NetworkX, Neo4j, GraphML.       |

In short:

```text
io/
  files and parsers

adapters/
  external runtimes and graph ecosystems
```

## Canonical scenario format

The recommended canonical scenario format has two main sections:

```yaml
entities:
  - id: org1
    type: Organization
    name: ExampleBank

relationships:
  - id: rel1
    type: operatesIn
    source: org1
    target: sector1
```

The file-level `id` values are **scenario identifiers**. They are used to connect entities and relationships during parsing.

They are not the same as the internal IDs generated by Python objects.

## Scenario IDs and internal IDs

Every entity and relationship instance receives an internal automatically generated ID.

When loading from a scenario file, there are two kinds of identifiers:

| Identifier  | Scope                             | Purpose                                       |
| ----------- | --------------------------------- | --------------------------------------------- |
| Scenario ID | File-level ID, such as `org1`.    | Used to connect relationships during parsing. |
| Internal ID | Generated by the object instance. | Used internally by the model and serializers. |

Example:

```yaml
entities:
  - id: org1
    type: Organization
    name: ExampleBank
```

When parsed:

```python
organization = Organization(name="ExampleBank")
print(organization.id)
```

The printed ID is generated internally and will not necessarily be `org1`.

The parser may keep a mapping such as:

```text
org1 → <generated-internal-id>
```

This design avoids exposing internal object identifiers while keeping scenario files readable.

## JSON scenarios

A JSON scenario follows the same structure as the canonical YAML format.

Example:

```json
{
  "entities": [
    {
      "id": "org1",
      "type": "Organization",
      "name": "ExampleBank"
    },
    {
      "id": "sector1",
      "type": "Sector",
      "name": "Finance",
      "taxonomy_ref": "sectors:finance"
    }
  ],
  "relationships": [
    {
      "id": "rel1",
      "type": "operatesIn",
      "source": "org1",
      "target": "sector1"
    }
  ]
}
```

Loading a JSON scenario:

```python
from metamodel.io.jsonParser import loadJsonScenario

model = loadJsonScenario("scenario.json")
```

After loading, validate the model:

```python
report = model.validate()

if not report.is_valid:
    for error in report.errors:
        print(error)
```

## YAML scenarios

YAML is often more convenient for case studies because it is easier to read and edit manually.

Example:

```yaml
entities:
  - id: org1
    type: Organization
    name: ExampleBank
    description: Example financial organization.
    source: Case study notes

  - id: sector1
    type: Sector
    name: Finance
    taxonomy_ref: sectors:finance

relationships:
  - id: rel1
    type: operatesIn
    source: org1
    target: sector1
```

Loading a YAML scenario:

```python
from metamodel.io.yamlParser import loadYamlScenario

model = loadYamlScenario("scenario.yaml")
```

YAML support requires the `yaml` optional dependency group:

```bash
pip install -e ".[yaml]"
```

or, from PyPI:

```bash
pip install "cti-feasibility-metamodel[yaml]"
```

## CSV scenarios

CSV support is useful for tabular inputs, but it is less expressive than JSON or YAML.

A practical CSV-based layout is to use separate files:

```text
entities.csv
relationships.csv
```

Example `entities.csv`:

```csv
id,type,name,description,taxonomy_ref
org1,Organization,ExampleBank,Example organization,
sector1,Sector,Finance,,sectors:finance
```

Example `relationships.csv`:

```csv
id,type,source,target
rel1,operatesIn,org1,sector1
```

Loading a CSV scenario could follow this pattern:

```python
from metamodel.io.csvParser import loadCsvScenario

model = loadCsvScenario(
    entities_file="entities.csv",
    relationships_file="relationships.csv",
)
```

CSV is recommended only for simple scenarios or data exported from spreadsheets. For richer case studies, prefer YAML or JSON.

## draw.io scenarios

draw.io files can be used when the scenario is first modelled visually.

A draw.io parser can extract:

* entity boxes;
* relationship edges;
* labels;
* cardinality annotations;
* diagram metadata.

Typical workflow:

```text
scenario.drawio.xml
        ↓
drawioParser
        ↓
Model
        ↓
validation
```

Example:

```python
from metamodel.io.drawioParser import loadDrawioScenario

model = loadDrawioScenario("scenario.drawio.xml")
```

After parsing, always validate:

```python
report = model.validate()
```

Visual diagrams may contain incomplete labels, missing endpoints, or ambiguous relationship names. Validation is therefore essential.

## STIX bundles

The package includes an extensible STIX parser.

STIX is used to represent and exchange cyber-threat intelligence. The parser maps STIX objects into CTI Feasibility Metamodel entities where a native correspondence exists and preserves other STIX objects generically.

### Loading a STIX bundle

```python
from metamodel.io.stixParser import loadStixBundleWithReport

result = loadStixBundleWithReport("bundle.json")

model = result.model

print(len(model.entities))
print(len(model.relationships))
print(result.skipped_objects)
print(result.skipped_relationships)
```

For a simpler API:

```python
from metamodel.io.stixParser import loadStixBundle

model = loadStixBundle("bundle.json")
```

### Native STIX mappings

The parser maps some STIX objects directly to native metamodel entities.

| STIX type        | Native metamodel entity |
| ---------------- | ----------------------- |
| `attack-pattern` | `TTP`                   |
| `campaign`       | `Campaign`              |
| `indicator`      | `Indicator`             |
| `intrusion-set`  | `Adversary`             |
| `malware`        | `AttackTool`            |
| `threat-actor`   | `ThreatActor`           |
| `tool`           | `AttackTool`            |
| `vulnerability`  | `Vulnerability`         |

Other recognized STIX objects are preserved as generic STIX entities.

### Generic STIX objects

When no native mapping is available, the parser can preserve the STIX object as:

```python
GenericStixObject
```

This avoids losing information.

Generic STIX objects store:

* STIX type;
* STIX ID;
* name;
* description, if available;
* raw STIX content;
* source metadata.

### STIX relationships

The parser supports the two STIX Relationship Object types:

| STIX relationship object | Handling                                                             |
| ------------------------ | -------------------------------------------------------------------- |
| `relationship`           | Preserved as `GenericStixRelationship` when endpoints are available. |
| `sighting`               | Preserved as `GenericStixRelationship` when endpoints are available. |

STIX relationships are preserved generically unless a safe native metamodel relationship mapping is implemented.

This is intentional. STIX relationship semantics do not always map one-to-one to CTI Feasibility Metamodel relationships.

## Extensible STIX parser

The STIX parser is registry-based.

Object mappers and relationship mappers can be registered without modifying the parser core.

```python
from metamodel.io.stixParser import StixParser

parser = StixParser()
```

### Registering a custom object mapper

```python
def map_course_of_action(stix_object, context):
    # Return a metamodel entity.
    ...

parser.register_object_mapper(
    "course-of-action",
    map_course_of_action,
)
```

### Registering a custom relationship mapper

```python
def map_uses_relationship(stix_relationship, context):
    # Return a list of metamodel relationships.
    ...

parser.register_relationship_mapper(
    "relationship",
    map_uses_relationship,
)
```

A mapper receives:

| Argument      | Meaning                                                         |
| ------------- | --------------------------------------------------------------- |
| `stix_object` | Raw STIX object dictionary.                                     |
| `context`     | Parser context containing the model and STIX-to-entity mapping. |

This makes the STIX integration extensible while preserving default behavior.

## Parser reports

Some parsers return a report object.

For STIX:

```python
result = loadStixBundleWithReport("bundle.json")
```

The result contains:

| Attribute               | Meaning                                             |
| ----------------------- | --------------------------------------------------- |
| `model`                 | Parsed `Model` object.                              |
| `stix_to_entity_id`     | Mapping from STIX IDs to internal model entity IDs. |
| `skipped_objects`       | Objects that could not be parsed or mapped.         |
| `skipped_relationships` | Relationships that could not be parsed or mapped.   |

A skipped object does not always indicate an error. It may indicate that no native mapping or generic fallback is available.

## Serialization

Serialization writes a model back to a file.

Example JSON serialization:

```python
from metamodel.io.jsonSerializer import saveJsonScenario

saveJsonScenario(model, "scenario.json")
```

Example YAML serialization:

```python
from metamodel.io.yamlSerializer import saveYamlScenario

saveYamlScenario(model, "scenario.yaml")
```

A serialized scenario should include:

* entities;
* relationships;
* entity attributes;
* relationship endpoints;
* type names;
* optional taxonomy references;
* optional source attributes on entities.

## Validation after I/O

Always validate parsed models.

```python
model = loadJsonScenario("scenario.json")
report = model.validate()

if not report.is_valid:
    for error in report.errors:
        print(error)
```

This is important because file-based scenarios can contain:

* missing entities;
* misspelled entity types;
* misspelled relationship types;
* invalid relationship endpoints;
* malformed taxonomy references;
* incomplete cardinalities;
* unsupported STIX mappings;
* ambiguous draw.io labels.

## Recommended workflow

For JSON or YAML scenarios:

```text
write scenario file
        ↓
load with io parser
        ↓
validate model
        ↓
fix scenario file
        ↓
export or analyze
```

For STIX bundles:

```text
load STIX bundle
        ↓
inspect parse report
        ↓
review skipped objects and relationships
        ↓
register custom mappers if needed
        ↓
validate model
        ↓
export or analyze
```

For draw.io diagrams:

```text
draw scenario
        ↓
parse draw.io XML
        ↓
review parsed entities and relationships
        ↓
validate model
        ↓
fix diagram or parser mappings
```

## Common issues

### `ModuleNotFoundError: No module named 'yaml'`

YAML support requires PyYAML.

Install the YAML extra:

```bash
pip install -e ".[yaml]"
```

### Scenario relationship points to an unknown entity

Problem:

```yaml
relationships:
  - id: rel1
    type: operatesIn
    source: org1
    target: sector1
```

but `sector1` is not defined in `entities`.

Fix:

```yaml
entities:
  - id: sector1
    type: Sector
    name: Finance
```

### Wrong import path

Use:

```python
from metamodel.io.jsonParser import loadJsonScenario
```

Do not use:

```python
from src.metamodel.io.jsonParser import loadJsonScenario
```

The package import name is `metamodel`.

### STIX relationship skipped

A STIX relationship may be skipped if one of its endpoints was not mapped.

Check:

```python
print(result.skipped_relationships)
```

Possible causes:

* the source object is missing from the bundle;
* the target object is missing from the bundle;
* the endpoint object failed to parse;
* a custom object mapper is needed.

### draw.io parsing ambiguity

A draw.io file may be visually clear but structurally ambiguous.

Common problems:

* missing edge labels;
* missing source or target endpoints;
* labels that do not match relationship class names;
* entity names that do not match metamodel class names;
* cardinalities encoded as visual text rather than structured edge metadata.

Use validation to detect these issues after parsing.

## Practical checklist

Before committing a file-based scenario:

* Does the file parse without errors?
* Are all entity types valid?
* Are all relationship types valid?
* Are all relationship endpoints defined?
* Are taxonomy references well formed?
* Does `model.validate()` return `is_valid = True`?
* Are skipped STIX objects or relationships documented?
* Are assumptions recorded in the case-study notes?
* Are generated outputs stored under `output/` and ignored by Git?
